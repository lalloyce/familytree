## 2. Findings carried into the design

Spike 1 (`spikes/leak/README.md`)

1. **A raw SQL role can read row counts.** As role `app_viewer`, `pg_stat_user_tables` showed different inserted-row counts in the world with a quiet claim and the world without. Consequence: viewers must never get a SQL session; M2 must confirm the exposed schemas leave out catalog and statistics data. How Supabase exposes schemas is [NEEDS SOURCE].
2. **SQLite's default leaves revoked bytes in the device file.** With `secure_delete=0` the revoked note, its person's name and both ids stayed in the file. With `PRAGMA secure_delete = ON` none remained (control run included). Consequence: the device database should set `secure_delete = ON`. The test used the rollback journal; WAL mode was not tested.
3. **Id derivation rule. PROPOSAL, NOT APPROVED.** The spike binds each id to its writer: the id must equal the first 16 bytes of `sha256(account || ':' || nonce)`, the nonce chosen by the client, and the server recomputes it before reading any table. Purpose: without it, inserting a row with a hidden claim's id would collide while a fresh id would succeed, an existence oracle for anyone who knows the id. The README calls the risk narrow, because knowing the id needs a prior leak or earlier access, and states one cost: a hash on each write. No canary demonstrates the oracle, so it is reasoning, not a test result. Three further costs, none in the README:
   - Design flow 1 says no account is needed until first sync or invite, so a row created offline before an account exists cannot carry an account-derived id (inference).
   - `derive_id` in `spikes/leak/schema.sql` casts the hash bytes to a uuid without setting version bits, so ids are not random version 4 UUIDs. Design section 8 says ids are client-generated UUIDs.
   - Every id is tied to its creator's account for good (inference).

   Alternatives (reviewer note): a writer-namespaced key `(created_by, id)`, or accept the oracle. Consequence: decide before the M2 schema is written. Section 8 is unchanged.
4. A visible claim whose base claim the viewer cannot see is sent with a null base. Not exercised by a test.
5. PL/pgSQL `exception when others` does not catch `QUERY_CANCELED` or `ASSERT_FAILURE`, so a `statement_timeout` inside `refresh_claim_access()` could escape the generic error and become an error-text channel. The README states this without a source [NEEDS SOURCE]. Consequence: M2 must account for it.

Spike 2 (`spikes/claims/README.md`)

6. **The supersession rule changed.** The Task 8 text superseded a claim only when it was the only active claim on its key. Under it, once a second account contested a fact, the first account could not correct its own claim: 119 to 149 own replacements stayed active per seed on seeds 1 to 20. The controller ruled the replacement rule `supersedeOwnUnderContest`: an asserter replacing their own active claim, named as the base, supersedes it whatever other accounts hold; replacing another account's claim never supersedes. It passes all four assertions on 200 seeds with 0 own replacements kept active. Consequence: the Task 8 tests and the wording of decision D change.
7. **Stale-base evidence.** A stale base (the base is on the server but no longer active) must be stored as a competing account. The counter `staleBase` ran 147 to 186 per seed under the ruled rule on seeds 1 to 20 (21 to 49 under the baseline). A negative control that lets a stale base supersede the asserter's current claim fails A2 (27 violations on seed 1) and failed on all 12 seeds tried when built on the ruled rule. The realistic trigger is one account on two phones replacing the same claim offline. A related rule: a claim overtaken in the queue that arrives after its own replacement is stored as superseded (`lateBase` fired once on each of the 200 ruled seeds). The README says the design should state it. One caveat: the fuzz's choice to target recent claims was added in a fix round, and whether it is needed is [NEEDS SOURCE] (README, "The fuzz").
8. **Merges refused while another merge stands (Findings 3 and 3b).** A merge or undo refused while one of its people is merged away stays refused after the undo. Under the ruled rule, of 12,822 replayed pairs, 823 differ in a way those in-window rows explain, and 2,061 are cascade pairs, where a refused merge's absence changes later merges and undos, sometimes on other people. The widest taint set held 175 merge and undo rows (baseline sweep). No claim status differs in any differing pair, and 0 pairs are non-cascade. **M5 question:** after undoing merge m, re-evaluate the merges refused while m stood (which can change outcomes people have already seen), or make every refused merge, and everything decided after it on the same people, a review task. Consequence: section 8's "review task" must cover conflicted merges and undos. The undo check is shown to catch a view-level bug, but no control shows it would catch a status-only merge or undo bug (README, "Limits of the undo check"), so the M5 build needs its own tests for retrying refused merges.
9. **Production sync estimate [ESTIMATE, not measured].** About 4 to 7 working weeks in all, 19 to 37 days. Work that exists only because the sync is custom: 12 to 23 days (about 2.5 to 4.5 weeks). Work needed whichever sync is used: 7 to 14 days (about 1.5 to 3 weeks). The sync core in the spike is 190 code lines of fake server (including the broken modes) and 114 of device sync code. The spike itself took minutes, which shows the core logic is small, not that the rest will be. **Section 9 triggers:**
   - "Custom sync costs more than a few weeks": not shown. Nothing in the spike measures weeks. The custom-only estimate straddles "a few", and the design does not say how many weeks that is. Borderline if the founder reads "a few" as three or fewer.
   - "PowerSync passes the leak spike": not tested. Spike 1 ran a custom Postgres model only. It has not fired, and there is no evidence either way.
10. Three sync requirements for M2 (Findings 4 to 6). Spike 1's per-account cursor moves only on access changes, so a status change such as superseded would never reach a device on it (inferred from the spike 1 README, not tested together). The fake server's global-log cursor would leak write counts, so use spike 1's per-account version. A permanently failing row needs a cap, a dead-letter state and a user-visible "not sent".
11. Contest keys use the raw person id, so while two people are merged their house claims sit on separate keys and never supersede each other, yet the merged view can show "accounts differ" across them.

Spike 3 (`spikes/invite/README.md`, `spikes/invite/matrix.md`)

12. **Token width.** 31^8 is 852,891,037,441 values, about 39.6 bits, and 2^40 is larger. A 40-bit token reduced modulo 31^8 is not one-to-one. Consequence: M3 issues 8-symbol values directly, or encode throws on a non-canonical token.
13. **Flow 4 claim visibility against section 9.** After redeeming and before confirmation, the redeemer sees the inviter's name and the claim text ("cousin of Otieno through his father"). Section 9 says the redeemer sees nothing of the tree until confirmation, and the claim names a tree person. Options: the inviter's name only; the claim with the named relative redacted; or as built. No test pins the choice. The README labels the flow 4 point "Founder decision", but section 6 does not mark flow 4 as founder decided (reviewer note, to confirm).
14. **The outbox must be persisted atomically.** M3 must persist the token pool and the outbox atomically with `take()` and must not clear the outbox after an `await`, or a binding added during the upload is lost. The demo holds all state in memory.
15. Guessing: the token space is about 8.5e11 values and a code alone gives no tree. Rate limiting on redemption is not simulated [inference, not tested].

Spike 4 (`spikes/tree/README.md`)

16. **Host proxy numbers and what the diagram cost depends on.** Numbers are in section 1. The focused layout's compute in the isolate had a median of 0.003 to 0.004 ms across the three runs, on a 12-node house. The README says its cost does not grow with the dataset, because the diagram draws one house, and that dataset size matters only for the copy into the isolate, which here copies all 3,000 people (the worst case; a real app would pass only the neighbourhood). The spike's real risks are the chain list and that copy, per the README. So the layout work does not depend on the dataset size. Inference: it depends on the size of the focused house, and only one 12-node house was timed. The height estimate used off the main thread was about 0.4 percent optimistic for the worst node on the Mac's system font and was not checked against Roboto. Host numbers cannot be scaled to a phone.
17. **"20 women in two houses" needs the founder's confirmation.** The plan asks for "20 women who appear in two houses". The generator reads it as 20 women who are wife in two houses under two different husbands. In the same model every married woman is also a child in her father's house, so a literal reading would cover every married daughter. Consequence: the synthetic data may under- or over-represent the case. Confirm the reading.

Spike 5 (`spikes/crypto/README.md`)

18. **Approach chosen.** SQLite3MultipleCiphers, bundled by the `sqlite3` package's build hook, with Drift's `NativeDatabase` unchanged. Sources read 2026-11-03: the Drift encryption page (recommends this for new apps and says `sqlcipher_flutter_libs` is no longer necessary from drift 2.32.0), the `sqlite3` 3.8.0 hook document, the SQLite3MultipleCiphers pragma and ChaCha20 pages, the flutter_secure_storage 11.2.0 README and source, and three Android backup pages. Observed: cipher `chacha20`, SQLite3MultipleCiphers 2.6.1, SQLite 3.54.0. The debug APK contains the library for three ABIs and was never run.
19. **Data-loss paths and the fallback now built.** The review found five ways the first version could destroy a database the stored key might still open. Now: a failed key read returns `keyReadFailed` and touches nothing; a missing or rejected key sets the file aside byte for byte instead of deleting it and never overwrites a stored key; only result code 26 triggers the fallback; a failed key write deletes only its own key name, not the whole store. Still removing or hiding data: flutter_secure_storage's own reset (`resetOnError`, default `true`), set-aside files nobody cleans up yet, and a restore without the key, by design. The real app still needs a user-confirmed "reset and re-sync" action for a key store that never reads again.
20. **Passphrase against raw key cost.** On the Mac the passphrase form cost about 14 to 15 ms more per open than the raw form (median against median). Inference: the raw form skips PBKDF2 key derivation; a phone's cost is unmeasured. The key is already 256 random bits, so derivation adds nothing for this design (the README's reading). Switching new installs is one line, but existing installs need a rekey migration, and the rekey syntax for the raw form was not checked. The README leaves the decision to the founder after the phone numbers.
21. **Android backup behaviour is untested.** Recommended manifest settings (`allowBackup="false"`, `dataExtractionRules`, `fullBackupContent`, the database in its own `files/db/` directory) are NOT tested. What a read returns after a restore (null, the string "Data has been reset", or an exception) is unknown. The founder's Android version is not known [NEEDS SOURCE].
22. **`resetOnError`.** The plugin default erases its stored data on a decryption error. The README recommends `resetOnError: false` so the error reaches the app, not tested. Reviewer note: with `false`, a restore that brings back the preferences but not the Keystore key could leave the app on `keyReadFailed` for good unless the preferences are excluded from backup or a user-confirmed reset exists. Also reviewer notes: a malformed stored key is a dead end of the same kind, and the README's test list has no test of `SecureKeyStore`'s `PlatformException` mapping.

## 3. Decisions

### Decision 1. PROPOSAL, NOT DECIDED: keep the custom sync or switch to PowerSync

Proposal: keep the custom sync behind `SyncTransport`, with `supersedeOwnUnderContest` as the contest rule. This is the spike 2 README's recommendation, and it matches the design's current call.

Evidence for: the sync core passed all four assertions on 200 seeds under each rule with every injected fault, and each assertion has a negative control that fails. Neither design trigger is shown (Finding 9).

What is not known:
- How many weeks "a few" is. The custom-only estimate of 12 to 23 days straddles it. This is the founder's to define.
- Whether PowerSync would remove the custom-sync-only items. The README marks this [UNVERIFIED].
- Whether PowerSync passes the leak spike. It was not run.
- Whether PowerSync works with a Drift-managed encrypted database, its cost and its sync-group limits. Design section 14 lists PowerSync with a Drift-managed database, its cost and its sync-group limits as not verified, and spike 5 did not attempt the encrypted case.
- Whether the estimate is right. It is not measured, and the spike touched no Postgres, HTTP or auth.

Finding 8 (the merge cascade) needs a design decision whichever sync is used, so it does not favour either option.

To settle it: the founder states "a few weeks" as a number, and someone runs PowerSync through the spike 1 scenarios and checks which custom-only items it removes.

### Decision 2. PROPOSAL, NOT DECIDED: do the weak-phone numbers force changes to the tree diagram

Answer: unknown until the phone is measured. The host proxy numbers (Finding 16) say nothing about a phone, and the README says they must not be used to predict a pass or a fail.

Proposal: change nothing in the diagram now. Measure first. Run the spike 4 phone procedure on the weakest pilot phone: `flutter run --profile -d <device>`, tap **Run benchmark**, three runs at the default system font and three at the largest, with battery, thermal and open-app conditions as the README lists. Record the model, Android version, RAM and date. Read `layout_ms.focused_end_to_end` (compare max, then p95, with 1,000 ms) and `scroll_frames_ms.total_span.p95` (compare with 16 ms), plus `whole_tree_end_to_end` and `frames_over_16ms`. Then run the spike 5 cold-start loop.

Inference: the host data points to the chain list and the copy into the isolate as the places to look first if the phone misses, not the diagram layout. Gaps to close if the diagram itself is to be judged: frames while scrolling or panning the diagram, and frames at text scale 2.0, were not measured.

### Decision 3. PROPOSAL, NOT DECIDED: does the typed code stay the primary invite path

Proposal: yes, keep it as the primary path and treat links as a convenience, as the design does.

Evidence: the design's reason is that a pilot app installed as a file has no install referrer, and how the pilot is distributed is unknown (design section 10). The spike does not contradict this. In simulation, a typed code works with no signal and shows nothing but "saved, we will connect when you have signal" (matrix rows 2 and 5). The checksum rejected every single-symbol substitution and adjacent swap tried (Section 1, spike 3).

What remains to test:
- All five matrix rows on a real phone, with the demo's Signal switch off and airplane mode on.
- Row 3 cannot run until link handling and Play Install Referrer reading are built.
- Whether relatives, older ones included, can type a 9-symbol code from a message or from speech. Not tested at all.
- Rate limiting on redemption, and persistence of the pool, the outbox and the redeem queue in the encrypted database.
- The flow 4 visibility question (Finding 13).
- How the pilot is distributed.

The spike shows the typed path works in logic. It shows nothing about whether links would work better or worse.
